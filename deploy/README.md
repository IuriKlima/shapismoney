Use a NEW application `shape-is-money`, NEW PostgreSQL database and dedicated volume/roles. No application user/admin is provisioned by migrations. 1. Verify Docker/container build and PostgreSQL 17 integration in an isolated environment before publication. This workstation has no Docker/psql/PostgreSQL executable; embedded PostgreSQL SQL tests do not validate network pg driver, image build, proxy TLS or backup/restore.
2. In the new EasyPanel service, source the approved new Git branch; build from repository root using `deploy/Dockerfile`. Runtime is independent Node, not the existing Vinext/Cloudflare process. 5. Run the one-shot migration service with `PGUSER=sim_migrator`, then start the app with `PGUSER=sim_app`. Migrations are transactional, versioned/checksummed and serialized by an advisory lock; unchanged repeat runs are harmless. 6. Set the canonical `SIM_PUBLIC_ORIGIN=https://...`, trusted proxy IPs and `SIM_PRODUCTION_REVIEWED=true` only after the review criteria pass. Production cookies are `__Host-`, Secure, HttpOnly and SameSite=Strict, with server expiry/revocation. Secrets are never printed in startup errors.
7. Check `/healthz` from inside the container (DB readiness), then login/CSRF/RBAC under the actual HTTPS domain. No seeds, demo data or tests are copied into the image. Provision the intended admin by a separately approved one-time secure handoff; there is no default password, auto-admin or public sign-up. Users cannot log in until provisioned.
8. AI is disabled by default. After approval of production API access, supply key only to the backend and set `SIM_AI_ENABLED=true`. `/api/local/ai` requires a valid session and coach/nutrition role. It sends only server-defined synthetic examples, never CRM data, and performs no writes. Local QA uses a mocked provider, no paid API calls. Context-aware AI, persistent nutrition, invites/email/reset and authenticated uploads remain future work; their absence must not be presented as ready.
9. Before go-live, validate restore from a dedicated DB backup, rollback to the approved image, proxy IP changes, origin redirects, session expiry/logout and cross-user denial. Container/image execution and real PostgreSQL transport remain unverified until run in an approved test environment. No deployment or changes to existing apps have been performed.

### Convites com entrega manual

O administrador autenticado gera convites somente na própria organização. Alunos são vinculados a cadastro existente com e-mail correspondente; profissionais usam um fluxo separado com personal ou nutrição, sem conceder administrador ou comprovar certificação. Nenhuma conta existente tem papel alterado. O administrador deve conferir a identidade do destinatário e entregar o código em canal privado; posse do código e e-mail correspondente autorizam a ativação, sem alegar verificação automática de caixa postal.

O aplicativo não configura SMTP nem envia e-mail. Código aleatório de 256 bits, validade de 30 minutos, hash SHA-256 no banco, retorno somente na primeira criação e nunca no cache de idempotência/auditoria. Novo convite invalida códigos anteriores do mesmo destinatário na organização. Ativação usa POST JSON com código/e-mail/senha de 14–128 caracteres definida pelo destinatário, consumo atômico e rollback completo quando o vínculo mudou. Limites por IP (8 ativações/15 min) e administrador (10 criações/15 min), proteção de origem e HTTPS mantidas. Código não entra em URL, localStorage, analytics ou referrer; a interface o apaga ao sair, ocultar ou perder sessão. Após ativar, entre normalmente e preencha onboarding.

Antes de atualizar o staging, aplicar **002-invitations.sql** usando somente `sim_migrator`, preservando banco/volume e as migrações antigas; a aplicação continua `sim_app`. Sem a migração nova, startup falha fechado pela conferência de checksums. Não iniciar deploy antes de preparar essa migração. Nenhum administrador, convite, código persistente ou destinatário real foi criado por esta implementação. Envio de e-mail, recuperação de senha e atribuição/reafetação de alunos a novos profissionais permanecem etapas separadas.

Assignment reuses existing columns and requires no migration or existing-data rewrite. Revoking a personal returns the student's record to the acting organization administrator; it does not assign a professional role to that administrator. Old professionals lose access on subsequent requests, including requests revalidated after taking the student row lock. PostgreSQL locks serialize assignment against onboarding and training writes. Existing published plans remain available to the student; unpublished plans lose approval and must be reviewed again by the new responsible professional.

Execution uses server-derived dates in `America/Sao_Paulo`, one session per student/day and a frozen prescription snapshot. Only the owner student may save today's prescribed set indices/repetitions/load; administrator and currently assigned personal may read execution/history, while nutrition and other students cannot. Recorded load has numeric input limits and never contributes to consistency. Repeated/no-op writes do not create additional set edits; revisions and row locks protect concurrent saves. Prior-day records are readable but not editable. The append-only edit history stores before/after records behind the same current assignment checks.

A professional sets prescribed weekly frequency (1–7 days; legacy plans default to 3). Weekly consistency uses completed daily sessions divided by the greatest prescribed target recorded that week, capped at 100%; changing load, adding attempts or training beyond the target adds no score. This is self-reported consistency, not a health or performance assessment. Ranking participation defaults off and requires the student to choose a pseudonym and consent. The organization ranking returns only alias and percentage; no names are supplied automatically, and no weights, repetitions, measurements, images, email or onboarding data are returned. Opt-out clears the public alias and excludes the student from the next uncached server query immediately.

Migration `003-execution.sql` creates only new workout/set/edit/consent tables and indexes; it does not alter or delete prior records, accounts or approvals. Apply through the existing dedicated migrator role before publishing the matching runtime, and verify all migration checksums and runtime role restrictions. Rollback planning must retain this additive migration in the runtime's expected migration catalog; rolling back to an image that expects only migrations 001–002 fails the startup checksum/catalog check.
