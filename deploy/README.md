Artifacts are prepared, not deployed. Preserve `medsi/app`, all askadia services, their volumes, databases, domains and secrets. Use a NEW application `shape-is-money`, NEW PostgreSQL database and dedicated volume/roles. No application user/admin is provisioned by migrations. Admin bootstrap and production secrets still require approval through a secure channel.

1. Verify Docker/container build and PostgreSQL 17 integration in an isolated environment before publication. This workstation has no Docker/psql/PostgreSQL executable; embedded PostgreSQL SQL tests do not validate network pg driver, image build, proxy TLS or backup/restore.
2. In the new EasyPanel service, source the approved new Git branch; build from repository root using `deploy/Dockerfile`. Runtime is independent Node, not the existing Vinext/Cloudflare process. Internal app port is `5190`; do not publish a raw host port. Domain must have HTTPS; proxy must preserve canonical Host and overwrite X-Forwarded-Proto/For. 3. Create a dedicated PostgreSQL service/volume. `deploy/compose.yaml` is a review example, not an EasyPanel import guaranteed to match its UI/network names. No database host port is published. Set actual existing proxy network name only after inspection. Do not assume the server is empty.
4. After explicit approval, supply independent bootstrap/migrator/runtime database passwords via server secret storage. The example init script creates `sim_migrator` as schema owner and `sim_app` as restricted runtime role. App receives ONLY runtime credentials; never bootstrap credentials. DB init runs only on a fresh volume; do not rerun against existing projects. Minimum password length is 20 characters. No production password/key is included in the repository.
5. Run the one-shot migration service with `PGUSER=sim_migrator`, then start the app with `PGUSER=sim_app`. Migrations are transactional, versioned/checksummed and serialized by an advisory lock; unchanged repeat runs are harmless. Runtime verifies exact migration checksums, rejects superuser/createdb/createrole/schema-create permissions and fixture accounts. Missing/changed migrations or failed DB connection stop startup; SQLite is never a fallback.
6. Set the canonical `SIM_PUBLIC_ORIGIN=https://...`, trusted proxy IPs and `SIM_PRODUCTION_REVIEWED=true` only after the review criteria pass. Default `SIM_DB_TLS=private-network` is for an explicitly isolated container DB hostname only; external DB requires `verify-full` and, if needed, a CA file. Never disable TLS verification. Production cookies are `__Host-`, Secure, HttpOnly and SameSite=Strict, with server expiry/revocation. Secrets are never printed in startup errors.
7. Check `/healthz` from inside the container (DB readiness), then login/CSRF/RBAC under the actual HTTPS domain. No seeds, demo data or tests are copied into the image. Provision the intended admin by a separately approved one-time secure handoff; there is no default password, auto-admin or public sign-up. Users cannot log in until provisioned.
8. AI is disabled by default. After approval of production API access, supply key only to the backend and set `SIM_AI_ENABLED=true`. `/api/local/ai` requires a valid session and coach/nutrition role. It sends only server-defined synthetic examples, never CRM data, and performs no writes. Local QA uses a mocked provider, no paid API calls. Context-aware AI, persistent nutrition, invites/email/reset and authenticated uploads remain future work; their absence must not be presented as ready.
9. Before go-live, validate restore from a dedicated DB backup, rollback to the approved image, proxy IP changes, origin redirects, session expiry/logout and cross-user denial. Container/image execution and real PostgreSQL transport remain unverified until run in an approved test environment. No deployment or changes to existing apps have been performed.

References: [node-postgres transactions](https://node-postgres.com/features/transactions), [TLS configuration](https://node-postgres.com/features/ssl), [official PostgreSQL image](https://hub.docker.com/_/postgres).


## Restricted HTTPS staging and manual initial administrator

To validate HTTPS/cookies/RBAC before production approval, use `NODE_ENV=production`, `SIM_DEPLOYMENT_STAGE=staging`, `SIM_PRODUCTION_REVIEWED=false`, canonical HTTPS origin and the actual trusted proxy IPs. Also set `SIM_STAGING_CLIENT_IPS` to exact reviewer public IPs only (comma-separated; no CIDR/wildcard). The application still enforces PostgreSQL least privileges, migrations, TLS proxy checks and Secure/HttpOnly/__Host-/SameSite cookies. Requests from other client IPs fail with 403. Container health probes remain available internally. Do not expose staging without this allowlist. Review actual HTTPS in this mode; only after it passes switch to `SIM_DEPLOYMENT_STAGE=production` and record approval with `SIM_PRODUCTION_REVIEWED=true`. Never set the approval flag merely to bypass a startup failure.

After explicit account-creation approval, the responsible person opens a secure SSH terminal or server shell over verified HTTPS and runs `node backend/bootstrap-admin.mjs` interactively in the application container as its normal non-root user. For Docker this can be `docker exec -it --user node <actual-app-container> node backend/bootstrap-admin.mjs`; use the actual container name, no password argument. The command uses the existing limited `sim_app` DB credential, validates migrations/role and needs no new database role, production secret or elevated grant. Remove/close temporary terminal access after the operation. Do not execute it over the unencrypted HTTP panel.

The command asks for organization/name/email, exact confirmation phrase and password twice with NO echo. User password is never accepted through arguments, environment, stdin redirection, logs or HTTP. Password is scrypt-hashed. Creation of organization, initial admin and audit event occurs in one transaction, serialized by advisory lock. Existing admin or nonempty installation is refused; there is no overwrite/reset/force mode. Recovery/replacement requires a separately reviewed procedure. No account is created at app startup or during migrations.

## Administração de alunos e treino

O administrador autenticado pode cadastrar alunos, registrar onboarding informado por eles e conduzir treino manual de rascunho até revisão, aprovação e publicação, somente na própria organização. O personal continua limitado aos seus alunos vinculados. O servidor verifica o papel na sessão; alterações de onboarding e treino exigem revisão atual e chave de idempotência, com auditoria. O onboarding direto do aluno continua restrito à própria conta.

Cadastro não cria conta, senha ou convite para o aluno. O administrador não recebe papel de nutricionista nem acesso à IA profissional automaticamente. Recuperação de senha, nutrição persistente e uploads seguem pendentes. Primeiro administrador continua exigindo bootstrap interativo e aprovação; não há seed ou conta automática.


### Convites com entrega manual

O administrador autenticado gera convites somente na própria organização. Alunos são vinculados a cadastro existente com e-mail correspondente; profissionais usam um fluxo separado com personal ou nutrição, sem conceder administrador ou comprovar certificação. Nenhuma conta existente tem papel alterado. O administrador deve conferir a identidade do destinatário e entregar o código em canal privado; posse do código e e-mail correspondente autorizam a ativação, sem alegar verificação automática de caixa postal.

O aplicativo não configura SMTP nem envia e-mail. Código aleatório de 256 bits, validade de 30 minutos, hash SHA-256 no banco, retorno somente na primeira criação e nunca no cache de idempotência/auditoria. Novo convite invalida códigos anteriores do mesmo destinatário na organização. Ativação usa POST JSON com código/e-mail/senha de 14–128 caracteres definida pelo destinatário, consumo atômico e rollback completo quando o vínculo mudou. Limites por IP (8 ativações/15 min) e administrador (10 criações/15 min), proteção de origem e HTTPS mantidas. Código não entra em URL, localStorage, analytics ou referrer; a interface o apaga ao sair, ocultar ou perder sessão. Após ativar, entre normalmente e preencha onboarding.

Antes de atualizar o staging, aplicar **002-invitations.sql** usando somente `sim_migrator`, preservando banco/volume e as migrações antigas; a aplicação continua `sim_app`. Sem a migração nova, startup falha fechado pela conferência de checksums. Não iniciar deploy antes de preparar essa migração. Nenhum administrador, convite, código persistente ou destinatário real foi criado por esta implementação. Envio de e-mail, recuperação de senha e atribuição/reafetação de alunos a novos profissionais permanecem etapas separadas.

For EasyPanel custom destinations, `tasks.medsi_shape-is-money:5190` avoids Swarm VIP source NAT. Traefik rewrites Host to that destination while setting X-Forwarded-Host to the public domain. Set `SIM_PROXY_UPSTREAM_HOST=tasks.medsi_shape-is-money:5190` only for this verified route, with `SIM_PUBLIC_ORIGIN=https://shapeismoney.com.br` and the exact trusted Traefik task IP. The app requires both the exact internal Host and canonical forwarded Host from that trusted peer; ambiguous forwarded chains and unapproved staging clients remain denied. Verify a real request through the public domain after each deployment; an internal probe alone does not prove browser access.
